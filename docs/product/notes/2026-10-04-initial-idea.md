# Initial idea (user's own words, verbatim)

Captured 2026-10-04, round 1 of the `/project-brief` interview. Do not edit: this is the source the brief and spec summary trace back to. Typos are the user's and are kept on purpose.

---

First of all, the project will have a backend (mainly a monolith, but should the need arise we could also introduce a few microservices), a web app, an electron app based on the web app , and most importantly a mobile app. and I think what we should start with are the backend, web app, and mobile app.

Here's how the idea goes:
The project is mainly mean to help with budget management. however that task is difficult and the amount of data entry it involves can be very frustrating, and lead to long nights of data entry or just completely ignoring the task all together. What the app can actually do to help with this is automatically track and collect all data regarding online payments and card-based transactions. 

First of all the app needs as many essential budget-tracking features as possible. and this can be tested through the webapp. This means a user, the user's accounts, shared accounts. Transactions, transfer of money between accounts. Actual accounts like bank accounts, online wallets, and other accounts like cash accounts. transactions obviously need to allow for a few things like a payee, the account that's being paid from, the purpose of the payment, tags for the transaction like "subscription" and any custom tags the user wants to add and transactions should be splitable into multiple transactions (cuz what if there's a complex amazon order that included food and tech items at the same time, then the purposes are different). this part is already many modules on its own, I believe. and the automation might be even bigger

There are many ways this can be done, however I was thinking that the easiest ways would involve connecting to the user's email account(s) (and we'll start with gmail), and their sms messages as well. that's step #1. Then we find all information regarding purchases/payments made or even subscriptions if possible. First we identify that some emails/messages are sent from the vendors/services the payment is being made to and some are made from the bank or payment gateway the payment is being made through. So sometimes the user receives multiple messages (with a small time gap between them) about the same transaction.
Other problems to take into account is that: we need the application to be able to read the amount and who the payment was made to from every message. but we want to do this smartly and efficiently. so my idea was that during the initial setup of the app (and maybe of each new account), the user will have to define where messages are coming from or allow ai (an llm) to automate that. we will provide both options for everything. This is because users might want to opt out of automation for privacy reasons. So the flow will involve identifying the messages that will be tracked.  it could be that the user wants all messages scanned for transactions only from specific senders. or that he wants to exclude all contacts from scanned messages by default with only defined exceptions. or that they don't mind all messages being scanned. obviously the permissions and privileges the application will have will probably allow it to scan and read all messages, but the goal here is to respect the user's privacy and boundaries. I also would love it if the app could represent your own debt and money that people owe you. This means if the other user exists you can represent a transfer to one of that person's accounts, and say that this is a loan (the other user as to accept it for this process to go through), or you could go ahead and just document it without the other person/entity existing in the system just to help you keep track of your stuff, and document it with some sort of deadline that asks you if you've made the payment need more time? or just need to update stuff regarding the debt. loans can be considered a transaction but can be marked as borrowing as in that it's expected to return to me or to return to the other side. it would also be nice if we can add refunds/returns as a concept, and link them to the previous outgoing transactions where the purchase was initially made. allowing the  user to also define that part of the thing was a tip is nice, but this can be achieved with easy using the tags/purpose and the sub-transactions, I assume. this is particularly important for users outside the US where tips are optional, and knowing how much you pay on them can be useful insight

All of these things should be something the user can setup and interact with simply through the application's web app and mobile app's uis, however they will allow the user to use automation and AI for them. However, one problem is that a lot of the time users forget to do data entry or are too lazy to. so that's why we're adding two different solutions for this:

1. some sort of reminder notifications based on the last time the user entered data and their desired preferences (this is especially important when cash is withdrawn and goes into a cash account)
2. We will introduce automation. this automation can be achieved using only just some templates, or with templates and LLM's, or maybe we could use system one models instead of llms, but we'll have to see


Then we need to read messages from the accounts/numbers that are likely going to be sending transactional information. And define certain templates for some of them. Again automation here is significantly preferred. Anyway, we start with one message from the bank (we want to focus on bank messages/emails as the source of truth or the primary source of information, as it reflects the state of the user's financial situation most accurately). use an llm or user input to find as many fields that can be fed in through the information in the message. linking it to an email or message from the vendor/service provider also helps fill in more details and would probably be based on linking accounts to different payees, so that would also be helpful. Some problems that might rise here is that the payee's name in the message is probably not the same as the common name the user uses for the payee, meaning that we need to link these names to payees in one to many relationship (many different names in the messages might mean one same payee). however while automating this process, the payee will get the name from correspondence by default (we will add to this later by using llms or some sort of categorization model to try and figure out what the category/purpose of the transaction is based on all the information available). And after we've defined the different templates (templates for cash withdrawl, money credited, money debited, payment made, whatever it is) we can go ahead and solidify the system later. and the user will be asked again for reviews to the automation later on, but i think reviews will be better than all of the manual data entry. and if there's a way to make the reviews very convenient that would be great. anyway... yeah go ahead with the project brief
